# План: история попыток учеников и контроль Telegram-доставки

**Feature**: `004-teacher-attempt-history`
**Status**: Implemented locally through Phase 4; Phase 5 requires migration approval
**Created**: 2026-09-02
**Depends on**: `003-student-attempt-grading`

## 1. Цель

Дать преподавателю защищённую страницу со всеми попытками прохождения принадлежащих ему
опубликованных уроков. Страница должна помогать быстро найти попытку, увидеть результат ученика,
проверить ответы и понять, был ли результат доставлен в Telegram.

Одновременно необходимо устранить разрыв между сохранением попытки и фоновой отправкой: успешная
проверка ученика не должна терять Telegram-событие, а оставшаяся в `pending` outbox-запись должна
быть автоматически обнаружена и обработана.

## 2. Пользовательский сценарий

1. Преподаватель входит в аккаунт и открывает пункт «Попытки» в профильном меню или из списка
   уроков.
2. Система показывает только попытки уроков этого преподавателя, начиная с самых новых.
3. Преподаватель ищет по названию урока или имени ученика и применяет фильтры.
4. В списке он видит урок, версию, ученика, дату, баллы и состояние Telegram-доставки.
5. При открытии попытки отображаются ответы в порядке исходного урока: введённое значение,
   правильность и принятые ответы для ошибочных полей.
6. Если Telegram-доставка не состоялась, интерфейс показывает безопасную причину и доступное
   действие восстановления.

## 3. Навигация и маршруты

- `/attempts` — список попыток преподавателя.
- `/attempts/[attemptId]` — детальная страница одной попытки.
- Ссылка «Попытки» в `TeacherProfileMenu`.
- Ссылка «Все уроки» на обеих страницах попыток.
- Ссылка «Попытки» в карточке опубликованного урока с заранее выбранным фильтром `lessonId`.

## 4. Страница списка `/attempts`

### Верхняя часть

- Заголовок «Попытки учеников».
- Общее число найденных попыток.
- Ссылка назад к `/lessons`.
- Профильное меню преподавателя.

### Поиск и фильтры

- Поиск по названию урока и имени ученика.
- Фильтр по конкретному уроку.
- Фильтр результата:
  - все;
  - полностью правильно;
  - частично правильно;
  - полностью неправильно.
- Фильтр Telegram-доставки:
  - все;
  - ожидает;
  - отправлено;
  - отключено/пропущено;
  - ошибка.
- Диапазон дат как последующее улучшение, если реальные объёмы покажут необходимость.
- Кнопка сброса фильтров.

Поиск и фильтрация выполняются на сервере. Их состояние хранится в query string, чтобы страницу
можно было обновить или отправить ссылку без потери выбранного представления.

### Строка/карточка попытки

- Название урока и номер опубликованной версии.
- Имя ученика.
- Дата и локальное время отправки.
- Результат `правильных ответов / всего` и процент.
- Текстовый статус результата, не зависящий только от цвета.
- Статус Telegram с понятной подписью.
- Кнопка «Посмотреть ответы».

На широком экране используется таблица, на телефоне — карточки. Сортировка по умолчанию: сначала
новые. Загрузка выполняется cursor-based страницами без получения всей истории в браузер.

## 5. Детальная страница `/attempts/[attemptId]`

- Название и версия урока.
- Имя ученика и серверное время попытки.
- Итоговый score и число правильных/ошибочных полей.
- Состояние Telegram-доставки и безопасная диагностическая причина.
- Группы и упражнения в порядке опубликованного `LessonSpec`.
- Для каждого поля:
  - ответ ученика;
  - `Правильно` или `Неправильно` с иконкой и текстом;
  - принятые значения, если ответ неправильный;
  - стабильные exercise/field IDs только в диагностическом раскрываемом блоке.

Страница должна поддерживать клавиатуру, мобильный layout и очевидный возврат к отфильтрованному
списку.

## 6. API-контракты

### `GET /api/attempts`

Query parameters:

- `cursor`;
- `limit` (по умолчанию 25, максимум 100);
- `query`;
- `lessonId`;
- `resultStatus`;
- `deliveryStatus`.

Ответ содержит student-safe для преподавательского интерфейса summary-массив и `nextCursor`.
`ownerId`, секреты Telegram, request fingerprint и полный `result_payload` наружу не передаются.

### `GET /api/attempts/{attemptId}`

Возвращает одну попытку и упорядоченные результаты полей. Доступ разрешён только владельцу урока,
определённому из серверной сессии.

### `POST /api/attempts/{attemptId}/telegram/retry`

Не реализуется до продуктового уточнения правил повторной отправки. Для неоднозначного provider
outcome повтор должен оставаться запрещённым, чтобы не создавать дубликаты.

## 7. Данные и индексы

Существующие таблицы остаются источником истины:

- `student_attempts`;
- `student_attempt_responses`;
- `telegram_delivery_outbox`;
- `lessons` и `lesson_versions`.

Новая миграция должна добавить только необходимые индексы, например:

- `student_attempts(owner_id, created_at desc, id desc)`;
- `student_attempts(owner_id, lesson_id, created_at desc)`;
- `telegram_delivery_outbox(owner_id, status, created_at desc)`.

Попытки и имена учеников продолжают храниться бессрочно согласно принятому решению. Страница не
добавляет удаление или изменение завершённой попытки.

## 8. Надёжная Telegram-доставка

### Fast path

После атомарного сохранения попытки приложение отправляет событие Inngest. Ошибка постановки
события записывается как sanitized telemetry и не влияет на ответ ученику.

### Recovery path

Периодическая Inngest-функция выбирает старые `pending` outbox-записи и инициирует их обработку.
Claim остаётся атомарным; одновременно одну доставку может обрабатывать только один worker.

### Классификация сбоев

- настройки отсутствуют или выключены → `skipped`;
- токен/Chat ID недействительны → `failed: unauthorized`;
- гарантированный `429` или `5xx` до принятия сообщения → ограниченный retry с backoff;
- timeout/обрыв после отправки с неоднозначным результатом → `failed: ambiguous`, без
  автоматического повтора;
- внутренняя ошибка чтения/дешифрования → `failed: internal` с sanitized observability.

### Длинные результаты

Сообщение разбивается по безопасным границам до provider limit. Summary всегда находится в первой
части; ответы одного поля не разрываются между частями. Для составной доставки сохраняются IDs
отправленных частей либо отдельные delivery-part записи.

## 9. Безопасность и приватность

- Каждый API route начинается с `requireTeacher()`.
- `owner_id` берётся только из проверенной серверной сессии.
- Admin Supabase client используется после owner-фильтра, а не вместо проверки владельца.
- Попытка другого преподавателя возвращает `404`, не раскрывая её существование.
- Bot Token, Chat ID, имя ученика, ответы и accepted values не попадают в логи.
- Поиск ограничивает длину, нормализуется и передаётся только через параметризованные Supabase
  запросы.
- Ответы API используют `Cache-Control: private, no-store`.

## 11. Acceptance criteria

- Преподаватель видит 100% сохранённых попыток только своих уроков.
- Новая попытка появляется в списке без ручной работы с базой.
- Поиск по уроку/ученику и фильтры возвращают корректные результаты после reload.
- Detail совпадает с неизменяемой опубликованной версией урока.
- Ни один cross-tenant тест не раскрывает чужую попытку или Telegram status.
- Потерянное первичное событие восстанавливается sweeper-ом.
- Длинный результат не отклоняется Telegram из-за превышения размера.
- Ошибка Telegram никогда не изменяет успешный grading response ученику.
- Все статусы доступны не только через цвет; mobile и keyboard journeys проходят.

6. Требуется ли агрегированная статистика по уроку уже в MVP или только список и detail?
